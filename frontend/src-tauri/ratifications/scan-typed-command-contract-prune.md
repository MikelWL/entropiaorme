# Ratification: manual skill-scan HTTP-contract pruning (typed-command migration)

Adversarial review of the OpenAPI contract deletion and corpus-replay retirement that accompany migrating the manual skill-scan route family (status, start, capture, cancel, undo, process, accept, reject, pending, the per-page capture-preview PNG, and the spacebar-capture toggle) off the in-process HTTP router onto typed Tauri IPC commands (ADR-0019). Re-derived against the current working tree; the change author's rationale is accepted nowhere on trust, because a self-approved golden move carries a structural conflict of interest. Two secondary claims in that rationale are corrected below (OR7, OR8); in both, the substantive conclusion nonetheless survives on independently verified grounds.

## Change under review

The scan family serves over `eo_api::scan` (`eo-api/src/scan.rs`) as typed DTOs on `impl Api`, dispatched by shell commands in `entropia-orme/src/commands.rs` plus the relocated bespoke `capture_png` in `entropia-orme/src/lib.rs`. Byte-parity is pinned inline in `eo-api/tests/scan_facade.rs`. The `/api/scan/skills/*` routes + adapters are deleted from the live HTTP router; the OpenAPI snapshot (`contracts/openapi.snapshot.json`) and the regenerated `frontend/src/lib/api/schema.d.ts` are pruned accordingly. `GET_scan_skills_status` is retired from the live-replay `endpoint_table` in `eo-http/tests/http_consistency_replay.rs` (its frozen goldens stay on disk). The single ratified contract movement: the status-shaped verbs return the full `ScanStatus` with `error` set on a logical refusal, where the HTTP body was the lone-key `{"error": ...}`.

## Oracle ratification audit

Range: `9376715..HEAD`. Every claim re-derived from source.

### Findings

**OR1, snapshot delta is a structurally strict pure deletion: genuine-spec-move.**
Parsed-structure diff (not raw lines, canonicalised deep-equal): exactly the 10 `/api/scan/skills/*` + `/api/scan/spacebar-capture` paths removed, zero added; exactly the 9 schemas `ProcessingProgress`, `ScanAcceptResult`, `ScanCaptureResult`, `ScanManualStatus`, `ScanManualStatusOrError`, `ScanRejectResult`, `ScanUndoResult`, `SkillScanPending`, `SpacebarCaptureResult` removed, zero added; zero surviving path object or schema altered; the top-level document minus `paths`/`components.schemas` is byte-identical after canonicalisation. The 15 "added" lines in the numstat are Myers re-anchoring of the `ReturnsBreakdown` survivor (`lootTt`/`pes`/`questPes`/`required`/`title`) around the deletion boundary, not semantic additions: `ReturnsBreakdown` is confirmed unaltered by the structural equality. A strict in-order subsequence.

**OR2, orphan reachability is exact and scan-caused; retentions correct: genuine-spec-move.**
No surviving `$ref` points at any of the 9 removed schemas, and no dangling `$ref` exists in the pruned document. `ProcessingProgress` (a leaf referenced only by the removed `Scan*Status*`/`ScanCaptureResult`/`ScanUndoResult`) is correctly swept with them. `/api/tracking/session/{id}/repair-scan` and `RepairScanResult` are retained (present in the working tree), consistent with repair-scan being tracking-session-scoped and migrating with the tracking family. `/api/scan/skills/capture/{page}` (the PNG) is confirmed absent from the parent snapshot (raw bytes, deliberately excluded), so its non-appearance in the delta is correct, not a silent drop.

**OR3, schema.d.ts is a clean regen of the same prune: genuine-spec-move.**
`0` added / `591` removed (numstat): a pure deletion, so no surviving type was mutated (a mutation would surface as an added line). All six scan-family type names are confirmed absent from the regenerated file. This is `gen:api` re-run over the pruned snapshot, nothing more.

**OR4, the refusal→full-status movement is a genuine, consumer-safe (indeed consumer-improving) contract change: genuine-spec-move.**
The success path is true byte-parity: the frozen Python-era wire body for `GET_scan_skills_status` (decoded from `basic_hunt_10_events/raw_captures/http_responses.json`) is `{"active":…,"processing":…,"captured_pages":…,"expected_pages":…,"last_scan_time":…,"skills_count":…,"configured":…,"game_window_present":…,"phase":…,"processing_progress":{"done":…,"total":…},"has_pending_result":…,"error":…}`, and `ScanStatus`'s field order (`eo-api/src/scan.rs:60`) reproduces it exactly; the facade pin `the_status_read_serialises_the_backend_way` asserts those identical bytes (only `game_window_present` differs, a fixture difference, not a shape one). The refusal movement is pinned by `a_refusal_returns_the_full_status_carrying_the_error`. Consumer safety re-derived at the one real UI site, `frontend/src/routes/scan-overlay/+page.svelte`: every mutating handler (`handleStart`/`handleCapture`/`handleUndo`/`handleCancel`, lines 238/252/270/287) reads `('error' in r && r.error)` first, then assigns `status = r`; all derived fields read defensively (`status?.phase ?? 'idle'`, `status?.captured_pages ?? 0`, `status?.processing_progress.done ?? 0`). Under the *old* contract a refusal set `status` to a bare `{error}`, collapsing every derived field to its fallback; the *new* full-status-plus-error assignment is therefore strictly better (the overlay retains the true current status while still surfacing the message). `scanStore.ts` consumes only the never-refusing `status` read and is unaffected. `game_window_present:false` is confirmed possible in a real refusal, so the superset is meaningful, not vacuous.

**OR5, disposition verbs preserve the polymorphic shape; first-generation pin, consumer-order-immaterial: genuine-spec-move (noted).**
`accept`/`reject` serialise `{ok, skills_persisted}` / `{ok}` on success and the lone `{error}` on refusal via `skip_serializing_if`, pinned in `accept_and_reject_preserve_the_polymorphic_shape`. A key-ordering caveat: these POST verbs are in no frozen golden (the replay `endpoint_table` is GET-only), so the byte-parity claim rests on the retired Python key order rather than a baseline oracle. This does not block: JSON object key order is not observable to the JS consumers, which are strictly key-based (`ScanReviewKindPane.accept` reads `result.error`; index.ts types by field name), so any hypothetical key-order divergence from Python is inert. The one order-sensitive oracle in the family (the status-read fingerprint) is separately verified byte-parity in OR4.

**OR6, corpus-replay retirement leaves every surviving fingerprint byte-unchanged: genuine-spec-move.**
`git status` shows zero byte changes under `fixtures/`; no golden file was edited or deleted, so `GET_scan_skills_status.json` stays frozen on disk in all seven scenarios. `GET_scan_skills_status` was confirmed the *last* tuple in `endpoint_table` (removed after `GET_tracking_session_quest_link_suggestion`); because the shared `Normalizer` accumulates symbols in encounter order and the four tracking reads precede the removed span, dropping the trailing entry cannot perturb any surviving fingerprint, and since `GET_scan_skills_status` carries no UUID/timestamp it seeded no symbol the survivors depended on. The cardinality guard rename `the_endpoint_set_is_the_fixed_five`→`_four` (5→4) is consistent, and no lingering `fixed_five` reference exists anywhere in `src-tauri`. The `consistency_scan_isolation_midpoint` scenario remains meaningful post-retirement (it still asserts the four tracking reads reflect scan-isolated state).

**OR7, rationale correction (`GET_scan_skills_status` IS referenced by `emitters_proof.rs`, but immaterially): inconsequential.**
The rationale's claim that `GET_scan_skills_status` is not referenced by the frozen `emitters_proof.rs` is **false**: it is curated endpoint #9 of the ten in `basic_hunt_10_events/raw_captures/http_responses.json`, and `http_fingerprints_match_committed_goldens` iterates all ten, fingerprinting the frozen base64 body and comparing to `expected/http_responses/GET_scan_skills_status.json`. This does not block: `emitters_proof.rs` replays *frozen Python-era captured bytes* through `eo_wire::http_fingerprint` and never builds the live router, so deleting the live scan route is entirely decoupled from it (the file is unmodified in the tree and still passes). The in-code comment in `http_consistency_replay.rs` ("their frozen Python-era fingerprint evidence stays in `eo-wire/tests/emitters_proof.rs`") is correct and consistent with this. Recorded so the mistaken claim is not carried forward as fact.

**OR8, rationale correction (`pending` has a real UI consumer, but the ordering change is invisible): inconsequential.**
The rationale's claim that pending has only test consumers is **false**: `frontend/src/routes/character/ScanReviewKindPane.svelte:44` calls `Object.entries(pending.skills)`. This does not block: line 54 immediately re-sorts the built rows via `sortByCorrection` (by absolute correction magnitude), and the name lookup at line 43 is a `Map` (order-independent), so the `SkillScanPending.skills` `BTreeMap` alphabetical order vs the HTTP first-seen order is not observable in the rendered output. No golden pins a multi-key pending payload (both `scan_facade.rs` and `index.test.ts` use single-entry payloads, `{"Rifle":100.0}` / `{Anatomy:12}`), so the ordering carries no oracle. The `None`→`null` (was HTTP 404) mapping is pinned and consumer-handled (`getManualSkillScanPending` maps to `SkillScanPending | null`, `ScanReviewKindPane` guards `if (!pending)`).

**OR9, determinism: clean.**
The facade pins use `RealClock`, but `last_scan_time` is `null` in every byte-asserted body (the status read, the refusal, and the capture-success pin all serialise `"last_scan_time":null`; undo/accept/reject/pending/spacebar/capture-png assert no clock-derived field). No wall-clock, randomness, environment, or timing input leaks into any pinned byte; the one ambient seam (the clock) is dominated to a constant by the empty/idle fixtures.

## Summary judgement

The snapshot delta is a structurally strict pure deletion (10 scan paths + 9 exactly-orphaned schemas removed, zero added, zero survivor mutated, envelope byte-identical, no dangling refs; the 15 numstat additions are Myers re-anchoring of an unaltered `ReturnsBreakdown`), and `schema.d.ts` is a clean regen of the same prune. `RepairScanResult`/repair-scan are correctly retained; the PNG was never in the snapshot. The single ratified behaviour movement (refusal returns the full status carrying `error` rather than the lone-key `{error}`) is genuine byte-parity on the success path (verified field-for-field against the frozen Python wire body) and, on the refusal path, consumer-safe and in fact consumer-improving: every overlay handler reads `.error` first and derives status defensively, so the superset upgrades the refusal render from a collapsed fallback to the true current state. The corpus retirement changed no golden byte and left every surviving fingerprint provably unchanged (trailing, symbol-free endpoint). Two secondary claims in the rationale are corrected (OR7: `emitters_proof` does exercise the scan status via frozen bytes, but is decoupled; OR8: `pending` has a live UI consumer, but its output is re-sorted), both immaterial to soundness on independently verified grounds. No ambient input enters any pin. Nothing in the delta is an unaccounted-for regression.
